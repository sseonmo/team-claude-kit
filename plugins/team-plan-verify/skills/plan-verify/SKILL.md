# plan-verify — 네 관점으로 플랜을 검증한다

## 이 스킬이 존재하는 이유

플랜을 여러 번 검증해도 **같은 각도로만 보면 같은 것만 잡힌다.**

- 사용자 관점만이 **기능이 통째로 없는 것**을 잡는다. 아키텍처 검증은 "있는 것이 잘 짜였나"를 본다.
- 과잉 관점만이 **앞선 검증이 만든 부채**를 청소한다. 없으면 검증할수록 플랜이 무거워지기만 한다.
- 그리고 넷 다 **한 문서 안에서만** 본다. 그 문서에 아예 없는 것은 비교 대상이 없어 못 잡는다.
  마지막 교차 대조가 그 층을 담당한다.

## 절대 원칙

1. **렌즈는 서로의 영역을 침범하지 않는다.** 겹치면 같은 지적이 네 번 나오고, 각자만 볼 수
   있는 것을 덜 보게 된다.
2. **렌즈 실행 중에는 파일을 쓰지 않는다.** 검증 대상 문서를 고치지 않는 것은 물론이고,
   렌즈의 산출물도 파일이나 Artifact 로 내보내지 않는다 — 응답 안에 초안으로만 낸다.
   발견을 모아 반영 단계에서 일괄 적용한다.
   렌즈마다 편집하면 호출 수가 10배가 되고 비용의 대부분은 편집에서 나온다.
3. **순서를 바꾸지 않는다.** 1이 기능 누락을 먼저 찾아야 2가 헛돌지 않고, 4는 2·3이 넣은
   것을 청소하므로 마지막이어야 한다.
4. **통과 목록과 "확인하지 못한 것"을 반드시 남긴다.** 발견만 나열하면 무엇을 안 봤는지 알 수 없다.
5. **커밋·푸시하지 않는다**(사용자 지시 전용).

## 준비 — 대상 확인과 스코프 판정

**검증 대상이 파일이라고 가정하지 않는다.** 셋 중 하나다.

| 대상 유형 | 예 | 처리 |
|---|---|---|
| 문서 세트 | `docs/` 의 PRD·ARCHITECTURE·ADR·USER_FLOW | 그대로 검증 |
| 플랜 파일 하나 | `plan.md`, `~/.claude/plans/*.md` | 그대로 검증 |
| **아직 파일이 없는 계획** | 방금 브레인스토밍·플래닝으로 합의한 것 | 먼저 한 벌로 정리해 보여주고 확인받는다 |

세 번째가 흔하다 — 플래닝이 끝난 직후가 검증하기 가장 좋은 시점인데 그때는 문서가 없다.
이 경우 검증에 들어가기 전에 **합의된 내용을 한 벌로 정리**한다. 흩어진 대화를 그대로 검증하면
렌즈마다 다른 것을 보게 되고, 대조 단계에서 A안이 무엇인지 특정할 수 없다. 정리본을 파일로
쓸지는 사용자가 정한다 — 안 써도 대화 안에서 고정되면 충분하다.

대상이 무엇인지 전혀 알 수 없을 때만 멈추고 묻는다.

**인자로 `full` 또는 `feature` 가 주어지면 그대로 쓰고 판정을 건너뛴다.** 없으면 세 신호를 본다.

| 신호 | FULL | FEATURE |
|---|---|---|
| 대상 범위 | 문서 3개 이상 또는 15,000 단어 이상 · 계획이면 주요 결정 10건 이상 | 문서 1~2개 / step 파일 하나 · 계획이면 결정 몇 건 |
| 새 외부 서비스·데이터 저장소 | 도입됨 | 없음 (기존 아키텍처 안) |
| 새 사용자 진입 경로 | 생김 | 기존 화면·API 수정 또는 하나 추가 |

- **3개가 한 방향(3/3 또는 0/3)** → 자동 판정. 근거 한 줄만 보고하고 진행한다. 묻지 않는다.
- **1~2개만 해당** → 신호별 판정을 보여주고 묻는다. 애매하면 FULL 을 제안한다 — 얕게 끝내는
  손실이 과하게 보는 비용보다 크다.

## 렌즈 1~4 — 순차 실행

`references/lenses.md` 를 읽고 순서대로 실행한다. 한 번에 하나씩, **앞선 렌즈들의 결정 표를
누적해서** 다음 렌즈에 넘긴다 — 직전 것만 넘기지 마라. 렌즈 4는 렌즈 1~3 전체의 결정 표를
받아야 한다. 자기검수가 "앞선 렌즈들이 추가한 항목을 전부" 재심사하는 일이라, 입력이 직전
하나로 잘리면 그 단계가 이름만 남는다.

넘기는 것은 결정 표뿐이다. 발견 상세와 통과 목록까지 다시 실으면 컨텍스트가 렌즈마다
불어나고, 비용의 대부분은 이 재읽기에서 나온다.

각 렌즈의 산출은 항상 이 형식이다. 다른 형식으로 내지 않는다 — 렌즈 4의 자기검수가 이 표를
입력으로 삼는다.

```
## 통과 — 확인했고 문제 없음
| 항목 | 무엇으로 확인했나 |

## 결정 표
| # | 항목 | 결정(제안) | 영향받는 문서 | 자동/질문 |

## 발견 상세 — 심각도 순
### [P0] (확신도 9/10) 한 줄 제목
- 위치: docs/X.md:12
- 실패 시나리오: <입력·상태> → <결과>
- 제안:

## 확인하지 못한 것
| 항목 | 이유 |
```

### 결정 권한 — 기준은 "대안이 열등한가, 다른가"

**[자동]** 방어 장치, 데이터 정합성, 사실 오류(틀린 근거·문서 간 모순·없는 참조).
묻지 않고 결정 표에 확정으로 올린다.

**[질문]** 제품 방향, 숫자를 정해야 하는 것(보관 기간·한도), 구현 비용과 이탈의 저울질.
트레이드오프를 양쪽 다 적어 그 렌즈가 끝날 때 한꺼번에 묻는다.

예외: 자동 대상이라도 되돌리기 비싼 변경(테이블·스키마 삭제, 문서 절 통째 교체)은
반영 전에 알린다.

## 반영 — 일괄

**파일을 고치기 전에 승인을 받는다.** "검증해줘"·"리뷰해줘"는 문서를 고쳐달라는 뜻이 아니다.
적용할 목록을 먼저 한 번에 보여주고, 사용자가 고치라고 했을 때만 파일에 손댄다.
사용자가 처음부터 수정까지 지시했다면 그 지시가 승인이므로 다시 묻지 않는다.

"자동"은 **묻지 않고 결정 표에 확정으로 올린다**는 뜻이지 묻지 않고 파일을 고친다는 뜻이
아니다. 이 둘을 섞으면 검토를 부탁한 사람의 문서가 조용히 바뀐다.

네 렌즈의 결정 표를 합쳐 중복을 제거하고 확정된 것만 한 번에 적용한다.

- 대상이 **파일**이면 문서를 고친다. 같은 문서를 여러 번 열지 않는다.
- 대상이 **아직 파일이 없는 계획**이면 확정본을 한 벌로 산출한다. 이 시점에는 문서로 남기는
  것이 자연스럽다 — 검증을 통과한 계획이고, 다음 대조 단계가 이 확정본을 A안으로 쓴다.
  어디에 쓸지는 사용자에게 확인한다.

## 대조 — 교차 설계 (FULL 기본 켜짐 / FEATURE 생략)

**FULL 이면 기본으로 실행한다. FEATURE 면 생략한다** — 기능 하나에는 대조할 독립 2안이
성립하지 않는다. FEATURE 에서 사용자가 명시적으로 요청하면 그때만 실행한다.

반영이 끝난 **최종본이 A안**이다. codex 에게 요구사항만 주고 독립 설계(B안)를 받아 대조한다.
목적은 좋은 안을 고르는 것이 아니라 **A안이 통째로 빠뜨린 것**을 찾는 것이다.

**전제 확인** — `which codex` 가 없거나 `~/.codex/auth.json` 이 없으면 **건너뛰고 그 사실을
보고한다.** 중단하지 않는다. (API 키는 필요 없다. `auth_mode: "chatgpt"` 면 구독 인증이다.)

**`which codex` 가 비면 그것이 결론이다. 다른 경로를 찾지 마라.** `find`·`ls`·`npm root`·
알고 있는 절대경로 실행 전부 금지다. PATH 에 없는 것은 설치되지 않았거나 사용자가 의도적으로
가린 것이고, 어느 쪽이든 대조를 건너뛰는 것이 맞다. 실측에서 이 탐색이 4회 일어나 결국
절대경로로 실행됐고, 그래서 스킵 경로가 한 번도 작동하지 않았다.

**요구사항만 추린다.** "무엇을 만드나"만. **아키텍처·데이터 모델·ADR 은 절대 넘기지 않는다** —
넘기면 베낀 답이 와서 대조가 무의미해진다.

**반드시 빈 디렉토리에서 실행한다.** 프로젝트에서 돌리면 sandbox 가 read-only 라도 codex 가
A안 문서를 읽어버린다.

```bash
cd "$(mktemp -d)"
TIMEOUT=$(command -v timeout || command -v gtimeout)   # 둘 다 없으면 타임아웃 없이 실행
if [ -n "$TIMEOUT" ]; then
  "$TIMEOUT" 600 codex exec --skip-git-repo-check "<요구사항 + 지시>" </dev/null
else
  codex exec --skip-git-repo-check "<요구사항 + 지시>" </dev/null
fi
```

**`</dev/null` 을 빠뜨리지 마라.** 프롬프트를 인자로 줬어도 `codex exec` 는
`Reading additional input from stdin...` 상태로 멈춘다. 비대화형으로 실행하면 EOF 가 오지
않아 타임아웃까지 통째로 대기하다 죽고, 겉보기에는 "codex 실패, 건너뜀"으로만 보고돼
원인이 드러나지 않는다. 실측에서 이 한 조각 때문에 600초를 버렸고, 붙이자 27초에 끝났다.

`timeout` 은 macOS 기본이 아니다(GNU coreutils). 없으면 `gtimeout` 을 쓰고, 둘 다 없으면
타임아웃 없이 실행한다 — 대조 하나 때문에 검증 전체가 멈추는 것보다 낫다.

**분기를 `if` 로 쓴 이유 — `${TIMEOUT:+$TIMEOUT 600} codex exec …` 로 줄이지 마라.**
bash 는 이걸 단어 분할해 정상 실행하지만 **zsh 는 기본적으로 단어 분할을 하지 않아**
`"/usr/local/bin/timeout 600"` 전체를 명령 이름 하나로 보고 `no such file or directory` 로
죽는다. macOS 기본 셸이 zsh 라 그 환경에서는 **항상** 실패한다. 실측에서 이 한 줄 때문에
첫 codex 호출이 통째로 죽었다.

지시 문안:

```
다음 요구사항만 보고 이 제품의 설계를 제안하라. 외부 파일을 읽지 마라.

<요구사항>

낼 것 — 산문 말고 목록으로:
1. 데이터 모델 (테이블과 핵심 컬럼, 중복 판정 키)
2. 처리 흐름 (단계와 각 단계의 실패 시 동작)
3. 사용자가 거치는 화면과 상태
4. 반드시 정해야 하는 결정과 네가 고른 답 + 이유
5. 이 요구사항만으로는 정할 수 없어 물어야 하는 것
```

**건너뛴다는 것은 대조 자체를 버린다는 뜻이다. 직접 B안을 만들지 마라.** 대조가 잡아내는 것은
"다른 모델이 봤으면 넣었을 것"이고, 같은 모델이 만든 B안은 A안과 사각지대가 상관되어 그 층을
못 채운다. 채운 것처럼 보이는 표만 남아 오히려 위험하다. 실측에서 codex 가 없자 스킵을 보고한
직후 "블라인드 B안"을 만들었고, 스스로 "같은 모델 계열이라 약하다"고 경고하면서도 만들었다.

타임아웃(600초)이나 쿼터 소진으로 실패하면 재시도하지 않고 건너뛴다.
**건너뛸 때는 원인을 함께 보고한다** — 명령 없음 / 인증 없음 / 타임아웃 / 비정상 종료 중
무엇인지. "대조 생략"만 적으면 환경이 고장난 것과 원래 안 도는 것이 구분되지 않는다.

**대조해서 두 가지만 뽑는다. 나머지는 버린다.**

| 유형 | 무엇인가 |
|---|---|
| **갈림** | A와 B가 배타적으로 다른 답을 낸 지점 |
| **공백** | 둘 다 정하지 않았거나, B가 "물어야 한다"고 짚은 것을 A도 안 정한 지점 |

**공백이 이 단계의 존재 이유다.** B안을 채택하지 마라 — 대조가 끝나면 버린다. "B가 더 낫다"를
논하기 시작하면 검증이 아니라 재설계가 되고 렌즈 넷이 쌓은 결정이 흔들린다. 뽑은 목록은
사용자 결정을 거쳐 추가 반영한다.

## 마무리

- **트레이드오프 기록** — 덜어냄·선택으로 감수한 것. ADR 후보다. 안 남기면 나중에
  "왜 이렇게 했지"가 반복된다.
- **확인하지 못한 것** 통합 목록. 대조를 건너뛰었다면 그 사실도 여기에 적는다.
- 지속 가치가 있는 결정 히스토리는 프로젝트 메모리에 남긴다.

## 함정

- **렌즈 1을 건너뛰지 마라.** "이미 유저 플로우가 있다"고 넘어가면 기능 누락이 끝까지 남는다.
- **렌즈 4가 아무것도 못 덜어내면 실패다.** 앞 라운드가 추가한 것이 첫 번째 후보다.
- **FEATURE 인데 새 문서를 만들지 마라.** 기존 문서에 절을 추가한다.
- **codex 를 프로젝트 디렉토리에서 실행하지 마라.** A안을 읽어 대조가 무의미해진다.
- **PATH 에 없는 codex 를 찾아내지 마라.** `which` 가 비면 그대로 건너뛴다.
- **codex 없이 B안을 직접 만들지 마라.** 같은 모델의 B안은 대조가 아니라 비용이다.
- **코드를 검증하려 하지 마라.** 이 스킬은 문서용이다.
