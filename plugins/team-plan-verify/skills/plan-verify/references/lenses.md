# 렌즈 프롬프트

## 공통 머리말 — 네 렌즈 앞에 붙인다

대상을 전부 읽고 시작한다. 읽지 않은 것에 대해서는 말하지 않는다.

모든 지적은 다음을 갖춰야 한다. 하나라도 못 쓰면 그 지적은 버린다.
- 위치: `파일:줄` 또는 섹션 이름 (파일이 없는 계획이면 항목 이름)
- 실패 시나리오: `<어떤 입력·상태에서>` → `<무엇이 잘못되는지>` 를 구체적으로
- 제안: 어떻게 고칠지 한 가지
- 심각도 P0(없으면 못 나감) / P1(구현 중 막힘) / P2(나중에 아파짐) + 확신도 1~10

없는 것을 추측으로 채우지 않는다. 없으면 "없다"고 쓴다.
확인한 것과 확인하지 못한 것을 반드시 구분해 남긴다 — 통과 목록이 없으면 무엇을 안 봤는지 알 수 없다.

출력 형식은 `SKILL.md` 의 "렌즈 1~4 — 순차 실행" 절에 있는 것을 그대로 쓴다. 여기에 다시
적지 않는 이유는 두 벌이 어긋나기 때문이다. 표 구조와 제목을 임의로 줄이지 마라 —
렌즈 4의 자기검수가 그 표를 입력으로 삼는다.

## 렌즈 1 — 사용자

사용자가 이 제품을 실제로 쓰는 경로를 전수로 추적한다.
user flow 와 상태 전이에 집중해, 모든 시나리오·가설·유즈케이스를 파악한다.

**반드시 할 것**
- 진입부터 이탈까지 모든 경로를 번호를 붙여 나열한다. 정상 경로와 예외 경로를 분리하고,
  각각에 사용자가 실제로 보게 될 화면과 문구를 적는다.
- 상태 전이를 상태 머신으로 그린다. 다이어그램을 함께 제시한다.
- **종점을 찾는다.** 사용자가 본류로 돌아오지 못하고 끝나는 경로가 어디인가.
  하나도 없다면 경로를 덜 본 것이다.
- **조용한 성공을 찾는다.** 시스템은 성공으로 처리하는데 사용자 눈에는 아무 일도 일어나지
  않은 것처럼 보이는 지점.
- **상태 이름과 실제 권한이 어긋나는 지점**을 찾는다. 이름만 보고 코드를 짜면 버그가 나는 곳이다.
- 사용자의 관심이 가장 높은 순간을 짚고, 그때 제품이 무엇을 주는지 확인한다.
  비어 있다면 그것은 UX 문제가 아니라 **기능 누락**이다.

**하지 말 것**
- 해피패스만 확인하고 끝내지 마라.
- 구현 방법이나 기술 선택을 논하지 마라. 다음 렌즈의 몫이다.
- 보안 취약점을 찾지 마라. 세 번째 렌즈의 몫이다.

**스코프별 조절** — FULL: 시나리오 전수·상태 머신·권한 매트릭스를 만든다. 각 시나리오에
인용 가능한 번호(S1, S2…)를 붙여, 이후 구현 지시가 문구를 다시 쓰지 않고 번호를 인용하게 한다.
/ FEATURE: 시나리오 목록만. 분기 3개 이상일 때만 다이어그램.

**이 단계에서는 파일을 쓰지 않는다.** 산출이 아무리 커도 응답 안에 초안으로 낸다.
파일·Artifact 로 내보내는 것은 반영 단계의 일이다(`SKILL.md` 절대 원칙 2). 렌즈 1은 산출이
가장 커서 여기서 문서를 쓰기 시작하면 호출 수가 폭증한다 — 실측에서 이 렌즈 하나가 110회
호출로 전체 비용의 절반을 썼고, 대부분이 분석이 아니라 편집이었다.
다이어그램은 Mermaid 로 응답에 담는다. Artifact 발행은 반영 단계에서, 그 기능이 있을 때만 한다.

## 렌즈 2 — 엔지니어

이 문서대로 구현하면 무엇이 깨지는지를 기준으로 본다.
테크 스택, 데이터베이스, 아키텍처 설계, 인터페이스가 제대로 잡혀 있는지 검증한다.

**반드시 할 것**
- **각 기술 선택의 근거를 검사한다.** 결론이 맞아도 근거가 틀렸으면 지적한다.
  틀린 근거는 나중에 누군가 그 결정을 뒤집을 때 잘못된 정보로 물려받는다.
- 런타임 실행 모델과 문서의 서술을 대조한다. 실행시간·메모리·동시성·rate limit 같은 제한을
  실제 수치로 계산해 문서의 주장이 성립하는지 확인한다.
- 데이터 모델: 기본키·유니크 제약·nullable·중복 판정 키·마이그레이션 필요 여부.
  중복 판정 키가 정의돼 있지 않으면 그것부터 지적한다.
- 인터페이스: 엔드포인트마다 입력·출력·호출 주체·권한 경계를 적는다.
- 같은 개념이 문서마다 다른 이름이나 다른 값으로 적혀 있는 곳을 찾는다.
  한 문서만 보면 멀쩡하고 같이 놓아야 드러난다.

**하지 말 것**
- "잘 되어 있다"로 넘어가지 마라. 무엇으로 확인했는지 쓰거나, 확인 못 했다고 써라.
- 스택 교체를 제안하지 마라. 이미 결정된 것 안에서 깨지는 지점을 찾아라.
- 성능 최적화를 제안하지 마라. 지금 필요한 것은 죽지 않는 설계다.

**스코프별 조절** — FULL: 전체 아키텍처·데이터 모델·실행 모델 대조표. / FEATURE: 이 기능이
닿는 경계만.

## 렌즈 3 — 실패·보안

엣지 케이스, 에러 케이스, 에러 핸들링, 보안 측면을 확인한다.
기준은 하나다 — 이것이 없으면 무엇이 뚫리거나 죽는가.

**반드시 할 것**
- 외부에서 도달 가능한 엔드포인트를 전부 나열하고, 각각에 인증·인가·서명 검증이 문서에
  명시돼 있는지 표로 확인한다. 명시가 없으면 "없음"이다.
- 신뢰 경계를 그린다. 사용자가 넣은 문자열이 어디까지 도달하는가 —
  프롬프트, 쿼리, 파일 경로, 스토리지 키, 외부 API.
- 식별자만 바꿔 남의 자원에 접근할 수 있는 경로를 찾는다. 행 수준 보안이 있어도 우회되는
  경로(관리자 권한으로 도는 곳)를 특히 본다.
- 각 단계가 실패했을 때 상태가 어떻게 남는지 추적한다. 부분 실패, 재시도, 중복 수신, 멱등성.
- 잘못된 값이 오류가 아니라 성공으로 처리되는 경로를 찾는다.

**하지 말 것**
- 일반 보안 체크리스트를 읊지 마라. 이 설계에 실재하는 경로만 다룬다.
- 이 제품 규모에 존재하지 않는 위협을 만들지 마라.
- "이것이 없으면 구체적으로 무엇이 가능해지는가"를 못 쓰면 그 항목은 버려라.

**스코프별 조절** — FULL: 도달 가능한 전 엔드포인트 × 방어 표. / FEATURE: 이 기능이
추가·변경하는 경로만.

## 렌즈 4 — 과잉

플랜이 단단하고 디테일해진 것은 좋다. 다만 **어느 규모까지 필요한가**가 기준이다.
오버엔지니어링했거나, 심플하게 갈 수 있는데 복잡하게 간 것이 없는지 검수한다.

**먼저 대상의 목표 단계를 확인하고 판정 근거를 한 줄 남긴다.** 대상이 단계를 명시했으면
(MVP·프로토타입·베타·운영 규모·SLA·트래픽 수치) 그것을 기준으로 삼는다.
**명시가 없으면 운영 규모로 가정한다.** 덜어낸 것을 다시 넣는 비용보다, 운영에 필요한 것을
MVP 기준으로 잘못 덜어냈다가 사고가 나는 비용이 크기 때문이다.
이 기본값 때문에 명시 없는 대상에서는 덜 덜어내게 된다 — 의도된 것이다.

**반드시 할 것**
- **자기 검수부터 한다.** 앞선 렌즈들이 추가한 항목을 전부 나열하고 하나씩 재심사한다.
  앞 라운드가 넣은 것이 이 라운드의 첫 번째 후보다.
- 각 항목에 묻는다: **위에서 정한 규모에서 이것이 실제로 작동하는가.**
  조건이 충족되지 않아 발동하지 않는 장치는 비용만 남고 효과가 0이다.
- 테이블·설정·추상화가 코드 상수나 컬럼 하나로 대체되는지 확인한다.
  대체되면 테이블·마이그레이션·조회 코드가 통째로 사라진다.
- **덜어내지 않기로 한 것도 이유와 함께 나열한다.**
- 덜어내서 생기는 트레이드오프를 명시하고 문서에 남긴다.

**하지 말 것**
- 앞 검증을 존중하느라 아무것도 덜어내지 못하면 이 라운드는 실패다.
  최소한 앞 라운드가 추가한 것 중 하나는 철회 후보로 검토해야 한다.
- 보안·데이터 정합성은 덜어내기 대상이 아니다.
- 지금 안 넣으면 나중에 마이그레이션이 필요한 것은 지금 넣는 쪽이 싸다.

**스코프별 조절** — FULL: 자기검수 + 전체 재심사. / FEATURE: 이번 라운드 추가분만.
