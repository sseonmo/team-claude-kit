# 재검증 — 같은 대상을 다시 볼 때

`SKILL.md` 준비 단계에서 재검증으로 판정되면 렌즈를 시작하기 전에 이 파일을 읽는다.

같은 대상의 이전 라운드 결과(결정 표·확인하지 못한 것·B안)가 대화, 프로젝트 메모리, 문서의
검증 이력 중 어디에든 있으면 재검증이다. 처음부터 전체를 다시 보지 않는다. 실측에서 같은 설계를
세 라운드 검증했는데 3차가 2차 결정 4건을 뒤집었고, 넷 모두 2차가 **반영한 변경**이었다. 그동안
codex 는 같은 요구사항으로 비슷한 B안만 다시 만들었고 반영한 변경은 한 번도 보지 못했다.

1. **직전 라운드의 "확인하지 못한 것"을 먼저 푼다.** 읽어서 확인되는 것은 확인하고, 사용자가 돌려야
   하는 것은 명령을 준다.
2. **범위는 직전 라운드 이후 바뀐 절과 직전 라운드가 추가한 결정이다.** 바뀌지 않은 절은 통과로
   이어받고 통과 표에 "이어받음"으로 적는다.
3. **렌즈 4 자기검수에 직전 라운드 추가분을 넣는다**(1건 1행).
4. **B안은 요구사항이 바뀐 때만 새로 만든다.** 아니면 이전 B안으로 대조한다. 이전 B안 파일이
   없으면 새로 만든다.
5. **codex 는 반영분 검토에 쓴다.** FULL 이면 기본으로 실행하고, 전제 확인·건너뛸 때 보고·
   재시도하지 않는 규칙은 대조와 같다. B안 생성과 목적이 반대다 — A안을 보는 것이 목적이므로
   **저장소 루트에서 `-s read-only` 로 실행해 대상 문서를 읽게 한다.** 직전 라운드 이후의 변경은
   `git diff <직전 검증 커밋> -- <대상 문서>` 로 뽑고, 커밋이 없으면 반영 목록을 바꾸기 전·후로
   정리해 넣는다.

```bash
REQ="$(mktemp)"; OUT="$(mktemp)"
{ cat <<'EOF'
<지시 문안>
EOF
git diff <직전 검증 커밋> -- <대상 문서>; } > "$REQ"
TIMEOUT=$(command -v timeout || command -v gtimeout)
if [ -n "$TIMEOUT" ]; then
  "$TIMEOUT" 600 codex exec -s read-only -o "$OUT" - < "$REQ"
else
  codex exec -s read-only -o "$OUT" - < "$REQ"
fi
```

지시 문안:

```
<대상 문서 경로> 는 설계 문서다. 아래 diff 는 직전 검증 뒤 바뀐 부분이다.
문서 전체를 읽고, 각 변경이 새로 만드는 실패를 찾아라 — 다른 절과의 충돌, 동시 실행·재시도·
재배포 중의 상태, 사용자가 본류로 돌아오지 못하는 경로.
파일은 읽기만 하고 수정하지 마라. 명령도 실행하지 마라. 새 기능은 제안하지 마라.

낼 것 — 문제 있는 변경만, 표로:
| 변경 위치 | 실패 시나리오(입력·상태 → 결과) | 심각도 P0~P2 | 고칠 방향 |
```

결과는 Claude 가 대상 문서와 다시 대조한 뒤, 렌즈 형식(위치·실패 시나리오·제안)을 갖춘 것만
발견으로 올린다. [자동]/[질문] 판정은 `SKILL.md` 결정 권한 기준을 그대로 따르고, 기능을 더하는 고침은
[질문]이다(`SKILL.md` 반영 절 "렌즈 4 뒤에 생긴 추가분").
