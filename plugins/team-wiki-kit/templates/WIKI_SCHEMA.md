# WIKI SCHEMA

이 저장소는 Andrej Karpathy의 **LLM Wiki** 패턴을 구현한 지식 베이스다.
RAG처럼 질문할 때마다 원본을 다시 뒤지는 게 아니라, **LLM이 위키를 점진적으로 만들고 유지한다.**
지식은 누적된다. 교차참조는 이미 걸려 있고, 모순은 이미 표시돼 있다.

역할 분담은 고정이다:
- **사람** — 소스를 고르고, 방향을 잡고, 좋은 질문을 한다.
- **LLM** — 나머지 전부. 요약, 교차참조, 정리, 기록.

> 이 파일은 `team-wiki-kit` 플러그인의 템플릿에서 생성됐다.
> **프로젝트에 맞게 고쳐 쓰는 것이 정상이다** — 카테고리, 소스 명명 규칙, 태그 체계는 팀마다 다르다.

## 3계층

| 계층 | 위치 | 소유자 | 규칙 |
|------|------|--------|------|
| 원본 | `raw/` | 사람 | **불변.** 읽기만 한다. 절대 수정·삭제하지 않는다. |
| 위키 | `wiki/` | LLM | 전적으로 LLM이 만들고 유지한다. |
| 스키마 | `WIKI_SCHEMA.md` (이 파일) | 공동 | 뭐가 잘 되는지 알아가면서 같이 고쳐 나간다. |

### 절대 규칙
1. `raw/` 안의 파일은 **어떤 이유로도 수정하지 않는다.** 새 소스 추가는 사람이 한다.
2. 위키 페이지의 모든 주장에는 출처가 붙는다. 출처 없는 주장은 쓰지 않는다.
3. 모순을 발견하면 **덮어쓰지 말고 표시한다.** 어느 쪽이 맞는지 모르면 양쪽 다 남기고 `> [!warning] 모순` 블록으로 적는다.
4. 추측을 사실처럼 쓰지 않는다. 소스에 없으면 없다고 한다.

## 디렉터리 구조

```
.
├── WIKI_SCHEMA.md         # 이 파일 — 스키마
├── raw/                   # 원본 (불변)
│   ├── <소스1>/
│   │   └── script.md
│   ├── <소스2>/
│   │   ├── script.md
│   │   └── slides/        # 있으면 도식·표 참고용
│   └── …
└── wiki/
    ├── index.md           # 전체 카탈로그 — 모든 페이지의 진입점
    ├── log.md             # 시간순 append-only 기록
    ├── concepts/          # 개념
    ├── people/            # 사람
    └── tools/             # 도구·제품·프로토콜
```

**소스 요약 페이지는 따로 두지 않는다.** 소스에서 나온 정보는 `concepts/`·`people/`·`tools/` 페이지로 직접 분배된다. 어떤 소스가 처리됐는지는 `index.md`가 기록한다.

새 카테고리가 필요하다고 판단되면 만들어도 된다. 단 `index.md`와 이 문서를 같이 갱신할 것.

`raw/` 하위 폴더명이 곧 소스 ID가 된다 (frontmatter의 `sources` 배열에 들어가는 값). 정렬 가능하고 사람이 알아볼 수 있게 짓는다 — 예: `ep01-제목`, `2026-03-저자-제목`.

## 페이지 형식

모든 위키 페이지는 YAML frontmatter로 시작한다.

```yaml
---
type: concept | person | tool
tags: [태그1, 태그2]
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: [<소스ID>, <소스ID>]
status: stub | draft | solid
---
```

- `sources` — 근거로 삼은 `raw/` 폴더명. 페이지가 갱신될 때마다 추가된다. **이 배열의 길이가 그 페이지의 신뢰도다.**
- `status` — `stub`(한두 줄), `draft`(소스 1~2개), `solid`(소스 3개 이상 교차 검증).
- `updated` — 페이지를 건드릴 때마다 반드시 갱신.

### 본문 규칙
- 한국어로 쓴다. 기술 용어·고유명사는 원어를 유지한다 (agentic engineering, harness, MCP).
- 다른 페이지는 `[[페이지명]]`으로 링크한다. 링크는 아끼지 말 것 — 아직 없는 페이지를 가리켜도 된다. 그건 "만들 가치가 있는 페이지" 표시다.
- 출처 표기: 문장 끝에 `(<소스약칭>)` 을 단다. 원문 인용은 `>` 블록으로, 출처와 함께.
- 페이지 하나는 화면 두세 개 분량을 넘기지 않는다. 넘치면 쪼개고 링크한다.

## 특수 파일

### `wiki/index.md`
전체 카탈로그. **모든 질의는 여기서 시작한다.** 카테고리별로 묶고, 페이지마다 링크 + 한 줄 요약 + 소스 수를 적는다.
어떤 `raw/` 소스가 ingest 됐고 안 됐는지도 여기서 관리한다.
ingest가 일어날 때마다 갱신한다. 이게 최신이 아니면 위키 전체가 망가진다.

### `wiki/log.md`
Append-only. 절대 기존 항목을 수정하지 않는다. 항목은 반드시 이 접두사로 시작한다:

```
## [YYYY-MM-DD] ingest | 제목
## [YYYY-MM-DD] query  | 질문 요약
## [YYYY-MM-DD] lint   | 점검 결과 요약
```

이 형식을 지키면 `grep "^## \[" wiki/log.md | tail -5`로 최근 이력을 바로 볼 수 있다.
각 항목 아래에 무엇이 바뀌었는지(생성/수정된 페이지 목록)를 불릿으로 남긴다.

## 3가지 동작

상세 절차는 `team-wiki-kit` 플러그인의 스킬에 있다.

| 동작 | 트리거 | 스킬 |
|------|--------|------|
| **Ingest** | "ep01 넣어줘", "소스 추가" | `wiki-ingest` |
| **Query** | 위키 내용에 대한 질문 | `wiki-query` |
| **Lint** | "점검해줘", 주기적으로 | `wiki-lint` |

## 작업 원칙

- **소스는 한 번에 하나씩** 처리하는 걸 기본으로 한다. 요약을 사람이 읽고 방향을 잡을 수 있어야 한다. 여러 개를 한꺼번에 넣어달라고 하면 그때만 배치로 한다.
- ingest 한 번에 **10~15개 페이지를 건드리는 게 정상이다.** 페이지 두세 개 만들고 끝내지 마라. 그건 일을 안 한 것이다.
- 질의 결과가 쓸 만하면 **위키에 페이지로 남긴다.** 좋은 분석이 대화 로그에 묻히면 안 된다.
- 위키는 git repo다. 의미 있는 단위로 커밋한다.
- `raw/*/slides/`의 HTML·PNG는 스크립트가 놓친 도식·표를 담고 있다. 필요하면 열어본다.
