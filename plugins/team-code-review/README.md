# team-code-review

변경 코드를 정확성·보안·아키텍처·테스트 커버리지 네 차원에서 리뷰하고, 발견을 검증 투표와 회차 기록으로 추적한다. 결과는 엔진이 집계하며 저장소 파일을 수정하지 않는다.

## 설치 및 요구 사항

```text
/plugin install team-code-review@team-kit
```

Node.js 20 이상과 Git이 필요하다. Claude Code Workflow 기능으로 리뷰를 실행한다. `gh` 는 `--pr` 또는 `--comment` 로 PR 정보를 조회·게시할 때만 필요하다.

## 구성

| 구성 | 경로 | 역할 |
|---|---|---|
| 스킬 | `skills/deep-review/SKILL.md` | 인수 처리, Workflow 호출, 결과 출력과 선택적 게시 |
| Workflow | `workflows/deep-review.js` | 네 차원 리뷰와 발견별 반박 검증 |
| 엔진 | `engine/` | 범위 필터, 투표 집계, 회차·판정·렌더링 |
| 명령 | `engine/cli.mjs` | `prepare`, `settle`, `skip` JSON 인터페이스 |

## 동작

대상은 상태에 따라 자동 선택한다. 경로를 지정하면 선택된 범위 안으로 리뷰를 제한한다.

| 상태/옵션 | 기준과 리뷰 대상 | 기본 모드 |
|---|---|---|
| 작업 트리가 dirty | `HEAD` 기준 staged·unstaged·untracked 변경. upstream 에 아직 보내지 않은 커밋은 포함하지 않는다. | fast |
| 작업 트리가 clean, upstream ahead | upstream 과 `HEAD` 의 merge-base 이후 커밋 변경 | fast |
| upstream 없음 | 기본 브랜치와 merge-base 이후 커밋 변경 | fast |
| `--pr` 또는 `--comment` | PR base 와 merge-base 이후 커밋 변경 | deep |
| 대상 변경 없음 | 리뷰를 시작하지 않고 종료 | 해당 없음 |

`--fast` 와 `--deep` 으로 기본 모드를 덮어쓸 수 있다. `--pr`/`--comment` 는 PR base 조회에 `gh` 가 필요하다. 작업 트리에 겹쳐 상쇄되는 staged/unstaged 변경만 남은 index-only 상태는 별도 차원 리뷰를 하지 않지만, 리뷰를 실행해 판정을 `Incomplete` 로 만든다.

| 옵션 | 시간 상한 | 발견별 검증 투표: critical / major / minor / nit |
|---|---:|---|
| `--fast` | 300초 | 2 / 2 / 0 / 0 |
| `--deep` | 480초 | 3 / 3 / 1 / 0 |

리뷰 차원은 정확성, 보안, 아키텍처, 테스트 커버리지다. 검증 대상은 fast 최대 10건, deep 최대 16건이며 완료된 차원 배치 안에서 심각도순으로 상한을 배정한다. 검증되지 않은 초과 발견은 결과에 미검증으로 남는다. nit 은 투표하지 않는다.

| 결과 | 동작 |
|---|---|
| `--skip <id> [메모]` | 해당 발견을 보류하고 즉시 종료한다. 이 실행에서는 리뷰하지 않는다. |
| 같은 입력 재실행 | 이전 원본 결과를 재사용하고 현재 보류·PR 상태로 다시 렌더링한다. `--fresh` 는 재사용을 건너뛴다. |
| 작업 트리 변경 | 결과는 표시하지만 회차 및 실행 기록을 저장하지 않는다. |
| `--comment` | 명시적으로 요청한 경우에만 연결된 PR 에 리뷰를 게시한다. PR 을 만들지 않는다. |

모든 상태 파일은 `$(git rev-parse --git-common-dir)/deep-review/` 아래에 둔다. 브랜치별 기록은 인코딩된 브랜치 이름의 `<branch>.json`, 실행 통계는 `runs.tsv` 다. pending, Workflow 결과, PR payload 도 같은 위치를 쓴다. detached HEAD 에서는 회차 기록과 runs 를 쓰지 않는다. 손상된 기록은 `.corrupt-<timestamp>` 파일로 옮긴다.

보류는 결함이라고 보지 않는 경우와 당장 고치지 않으려는 경우를 구분하지 않는다. 메모만 덧붙일 수 있다. 첫 대응 리뷰의 코드 상태를 snapshot 으로 고정하고, 그 코드가 바뀌면 보류가 풀린다. 보류한 판단이 충돌 상대를 채택한 경우 반대쪽의 왕복 발견을 접는다. 재사용과 보류는 새 회차나 runs 행을 만들지 않는다. 보류 해제 CLI 는 없으므로 실수로 보류했다면 현재 브랜치 JSON 의 `skips` 에서 해당 id 를 직접 지운다.

## 알려진 한계

| 제한 | 영향 |
|---|---|
| Workflow 가 필요하다 | 사용 가능한 Workflow 도구가 없으면 실행을 멈춘다. 대체 실행 경로는 없다. |
| 모델 리뷰 품질에 의존한다 | 엔진은 범위와 투표를 집계하지만 발견 자체의 정확성을 보장하지 않는다. |
| 미검증 발견도 판정에 들어간다 | 검증되지 않은 critical/major 발견도 verdict 에 영향을 줄 수 있다. 검증 상한을 넘은 항목은 미검증으로 표시된다. 시간 종료로 끝나지 않은 차원은 실패로 표시된다. |
| 큰 diff 는 거부하지 않는다 | 변경 2,650줄을 넘으면 시간 경고만 표시한다. 경로 인수로 나눠 실행할 수 있다. |
| dirty 리뷰 범위는 커밋을 뺀다 | dirty 상태에서는 `HEAD` 와 작업 트리 차이를 보므로 upstream 에 아직 보내지 않은 커밋은 대상이 아니다. |
| index-only 변경은 별도 검사하지 않는다 | 겹쳐 상쇄되는 staged/unstaged 변경을 별도 차원으로 리뷰하지 않고 판정을 `Incomplete` 로 표시한다. |
| 결과 원본 보관은 제한적이다 | 작업 트리가 리뷰 중 바뀌면 결과를 표시하지만 회차와 runs 에 저장하지 않는다. 이전 회차 기록을 자동 정리하지 않으며 실행별 원본 아카이브도 만들지 않는다. |
| 보류는 사용자 기록이다 | 잘못 보류한 항목은 기록 JSON 에서 직접 제거해야 한다. |
| GitHub 게시 조건이 있다 | `gh` 인증과 연결된 PR 이 필요하다. 422 응답은 상세 본문을 한 번 재시도한다. |
