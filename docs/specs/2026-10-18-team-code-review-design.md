# team-code-review — 수렴하는 다차원 코드 리뷰를 플러그인으로

2026-10-18 · 신규 `plugins/team-code-review/` · 스킬 `deep-review`
원형: FinSight `.claude/commands/review-code.md` + `.claude/workflows/review-code.js`

## 왜 만드나

FinSight 의 `/review-code`(3개 차원 동시 리뷰 → 발견마다 반박 검증 → 결정론적 판정 → PR 게시)를
다른 저장소에서도 쓰고 싶다. 사용자는 혼자 쓰고, 커밋 전·push 전·PR 세 시점에 **직접 부른다**(게이트 아님).

원형을 쓰면서 겪은 문제가 이 설계의 출발점이다:

1. **틀린 리뷰** — 없는 결함을 지적하거나 심각도를 부풀린다. 반박하면 AI 가 "제가 틀렸습니다" 라고 물러선다.
2. **범위가 샌다** — 리뷰 대상은 이번 커밋·push·PR 인데, 기존 코드의 문제까지 발견으로 올라온다.
3. **끝나지 않는다** — 지적을 고치면 다음 회차가 그 수정을 다시 틀렸다고 한다. 고치고 → 지적받고 →
   고치는 반복에 시간이 무한히 든다.

목표는 **리뷰가 수렴하는 것**이다. 같은 변경을 두 번 리뷰하면, 두 번째는 새로 생긴 진짜 문제만 말해야 한다.

## 목표 / 비목표 / 반목표

목표
- 이번 대상의 diff 에 있는 줄만 발견으로 보고한다 (결정론적으로 강제)
- 회차를 기억해, 이전 판단과 뒤집히는 지적을 "고쳐라" 가 아니라 "판단 충돌" 로 보여준다
- 빠른 모드 5분, 정밀 모드 8분 안에 결과를 낸다
- 프로젝트 규칙은 그 저장소의 `CLAUDE.md`·`AGENTS.md` 에서 읽는다 — 플러그인에 박지 않는다

비목표
- git 훅·게이트로 자동 실행 (커밋·push 게이트는 별도 플러그인에서 다룬다)
- 팀원 간 리뷰 기록 공유 (혼자 쓴다)
- 저장소 전체 감사, 커버리지 수치 측정

반목표 — 기술적으로 동작해도 이렇게 되면 실패다
- **파일을 고친다.** 리뷰가 스스로 고치기 시작하면 무한 반복이 자동화된다. 읽기만 한다.
- **진짜 버그를 숨긴다.** 반복을 줄이려고 고친 줄을 리뷰에서 빼면 수정이 만든 새 버그를 놓친다.
  고친 줄도 똑같이 리뷰한다 — 막는 것은 재지적이 아니라 *판단의 왕복*이다.
- **시간이 넘었다고 아무것도 안 낸다.** 상한에 걸리면 남은 검증을 `미검증` 으로 두고 결과를 낸다.

## 원형에서 그대로 가져오는 것

원형의 동작을 바꾸지 않고 옮긴다. 세부는 원형 두 파일을 그대로 참조할 것.

- 차원별 리뷰어를 동시에 돌리고, 차원이 끝나는 즉시 그 차원의 발견을 검증한다 (`pipeline`)
- 검증자는 **반박하는 쪽**에서 시작하고, 관점(lens)을 나눠 받는다
- 검증자는 심각도를 **내리기만** 한다. 과반은 **배정 인원** 기준. 검증자가 죽어 과반 미달이면 `unverified`
  로 남기고 판정에 넣는다 (인프라 오류가 결함을 지우지 않는다)
- 판정 표: critical ≥1 → Blocked / major ≥1 → Changes Requested / 그 외 → Approve
- 실패한 차원은 `⚠ <차원> 차원은 실행되지 않았다` 로 반드시 드러낸다
- 출력 2층(발견 1건당 4줄 코멘트 + 요약 1개), 심각도 아이콘, `[minor ← major]` 표기
- `--comment` PR 게시: `event: COMMENT` 고정, `commit_id = headRefOid`, 로컬≠PR head 또는
  uncommitted 가 있으면 인라인 생략, 422 시 body 만으로 재시도, PR 이 없으면 만들지 않는다
- 거짓 양성 금지 지시("확실하지 않으면 보고하지 마라", "발견 0건은 정상")

## 바뀌는 것

### 1. 대상 — 자동 선택

인수가 없으면 실행 시점 상태로 정한다. 인수로 덮어쓸 수 있다.

| 상태 | 대상 | 모드 기본값 |
|---|---|---|
| uncommitted 변경이 있다 | staged + unstaged | 빠른 |
| 없고, upstream 보다 앞선 커밋이 있다 | `@{upstream}...HEAD` | 빠른 |
| upstream 이 없는 브랜치 | `<기본 브랜치>...HEAD` | 빠른 |
| `--pr` 또는 `--comment` | `<PR base>...HEAD` (+ uncommitted) | 정밀 |
| 대상 0건 | 리뷰하지 않고 알리고 끝낸다 | — |

- 기본 브랜치는 `git symbolic-ref refs/remotes/origin/HEAD` 로 감지한다. 실패하면 `main`, `master` 순으로 찾는다.
  `main` 을 박지 않는다.
- 원형의 구멍(main 위에서는 uncommitted 만 보고 push 안 한 커밋을 놓침)을 위 표가 메운다.
- PR base 는 `gh pr view --json baseRefOid` 의 **커밋 SHA 로 고정**하고 그것과 HEAD 의 merge-base 를 쓴다. 로컬 `main` 은 물론
  fetch 하지 않은 `origin/<base>` 도 낡을 수 있어, 이미 기본 브랜치에 병합된 변경까지 PR 범위에 들어온다. 그 객체가 로컬에 없으면
  추측하지 않고 `git fetch origin <base>` 를 안내하며 멈춘다(스스로 fetch 하지 않는다). *(Codex 2차 검증 반영)*
- **untracked 새 파일도 uncommitted 에 넣는다**(`git ls-files --others --exclude-standard`, `.gitignore` 존중).
  diff 는 `git diff --no-index /dev/null <파일>` 로 만든다. `git add -N` 처럼 index 를 건드리는 방법은 쓰지 않는다
  (읽기 전용). *(설계자 판단: 커밋 전 리뷰가 주 시점이고 Java 는 새 클래스 파일이 흔하다 — 원형은 이를 놓쳤다)*
- 인수: `--fast` / `--deep` (모드 강제), `--pr`, `--comment`, `--skip <id> ["이유 메모"]`, `--fresh`, 경로 토큰(대상 파일 제한).
- **push 전 범위를 강제하는 인수는 두지 않는다**(사용자 결정). uncommitted 가 있으면 대상은 그것뿐이다 — 감수하는 트레이드오프 절 참고.
- **큰 diff 는 시작 전에 경고만 한다**(사용자 결정). 변경 줄 수가 기준을 넘으면 "5분 안에 끝나지 않을 수 있다 — 경로 인수로
  나눠 리뷰하라(예: `/deep-review src/order/`)" 를 알리고 그대로 진행한다. 거부하지 않는다. 기준값은 스파이크에서 정하고
  이후 `runs.tsv`(§7)를 보고 사람이 조정한다.
- **코드가 그대로면 지난 결과를 다시 보여준다**(사용자 결정). 마지막 회차와 다음이 **전부** 같을 때만 리뷰를 돌리지 않고
  `변경 없음 — R3 결과를 다시 보여줍니다` 와 함께 그 결과를 낸다(보류 상태는 현재 기록으로 다시 반영). AI 리뷰는 같은 코드에도
  매번 조금씩 다른 지적을 내므로, 이것이 반복의 씨앗 하나를 없앤다. `--fresh` 로 강제 재실행.
  - 재사용 키: **HEAD SHA · 기준 커밋 SHA** · 대상 diff 해시 · untracked 내용 해시 · index 해시 · 모드 · 적용된 `CLAUDE.md`·`AGENTS.md`
    내용 해시 · 플러그인 버전. diff 가 같아도 HEAD 쪽 의존 코드(예: boolean 을 반환하던 함수가 객체를 반환하게 됨)가 바뀌면 같은
    변경이 새 버그가 되므로 diff 해시만으로는 부족하다. *(Codex 2차 검증 반영)*
  - **재사용은 리뷰 실행만 생략한다.** 출력·PR 확인·`--comment` 게시 단계는 그대로 진행한다 — `--pr` 로 터미널에서 본 직후 같은
    코드에 `--comment` 를 부르면 게시까지 가야 한다. 재사용 결과를 게시할 때도 게시 규칙(`headRefOid`·인라인 앵커 전제)은 그대로다.
    *(Codex 2차 검증 반영)*

### 2. 범위 필터 — 결정론적

원형은 리뷰어에게 "변경된 줄만 보지 말고 의존 코드를 확인하라" 고 지시한다. 이 지시는 **유지한다**
(정확도를 위해). 대신 **보는 범위와 보고하는 범위를 분리**한다.

- **diff 는 하나만 만든다 — 기준 커밋 → 현재 작업 트리.** `git diff <기준 커밋>`(두 번째 인자 없이 = 작업 트리와 비교,
  staged·unstaged 포함) + untracked 파일. 기준 커밋은 대상 표의 행에 따라 `HEAD` / upstream / 기본 브랜치와의 merge-base /
  PR base 와의 merge-base 다. 커밋 범위 diff 와 미커밋 diff 를 따로 만들어 줄 번호를 합치지 않는다 — 두 diff 는 좌표계가
  달라서, 커밋에서 바꾼 5행 앞에 미커밋으로 두 줄을 넣으면 실제 대상은 7행인데 합집합은 5행을 남긴다(Codex 검증, git 으로 재현).
- **단, 이 diff 는 index 를 보지 않는다.** 권한 확인 줄을 지워 stage 한 뒤 작업 트리에서만 되살리면 `git diff HEAD` 는 비어 있지만
  다음 커밋에는 삭제가 들어간다. 그래서 대상 선정 때 **index 에만 있는 변경**(HEAD→index 에 있는데 HEAD→작업 트리에는 반영되지
  않은 변경)을 따로 찾는다. 있으면 그 파일을 결과 맨 위에 `⚠ 커밋될 내용(index)이 리뷰한 내용(작업 트리)과 다르다` 로 알리고,
  판정이 Approve 였다면 `Incomplete` 로 낸다. 작업 트리가 index 를 포함하는 흔한 부분 stage(`git add -p` 후 추가 편집)는 경고하지
  않는다. index 를 따로 리뷰하지는 않는다 — 리뷰어 도구는 작업 트리를 읽으므로 두 번째 좌표계가 생긴다. 판별 방법은 빌더에게
  맡긴다. *(Codex 2차 검증 반영 · 설계자 판단)*
- **위치 모델** — 발견의 위치는 `{ path, oldPath?, side: 'new' | 'old', line }` 이다.
  - `side: 'new'` — 변경 후 파일 좌표. 범위는 그 파일의 `+` 줄.
  - `side: 'old'` — 변경 전 파일 좌표. 범위는 `-` 줄. **줄을 지운 것 자체가 결함인 경우**(예: 권한 확인 줄 삭제 —
    보안에서 가장 위험한 종류)와 **파일 전체 삭제**를 여기로 표현한다. 앵커할 변경 후 줄이 없어도 잃지 않는다.
  - 이름 변경은 `oldPath` 로 이어 준다.
  - PR 게시 때 `new` → `side: RIGHT`, `old` → `side: LEFT`.
  *(Codex 검증 반영: 처음 안의 "삭제 블록 다음 줄에 앵커" 는 파일 전체 삭제를 표현하지 못했다)*
- 리뷰어 스키마도 이 위치 모델로 받는다. 리뷰어에게 "삭제된 코드를 지적할 때는 `side: 'old'` 와 변경 전 줄 번호" 를 쓰게 한다.
- **변경 때문에 기존 코드의 결함이 새로 도달 가능해진 경우**, 결함이 있는 줄은 diff 밖이어도 원인은 diff 안에 있다. 리뷰어에게
  "그 원인이 된 변경 줄을 위치로 쓰고, tldr 에 결함이 있는 기존 위치를 적어라" 고 지시한다. 그래야 범위 필터가 이런 진짜 버그를
  버리지 않는다. 원인이 이번 변경에 없는 기존 결함은 여전히 범위 밖이다. *(Codex B안 대조에서 나온 공백 반영)*
- 리뷰어·검증자가 낸 발견 중 위치가 범위 밖인 것은 **버린다.** 리뷰어 지시에 맡기지 않는다 —
  지시로는 지켜지지 않았던 것이 원형의 문제였다.
- 버린 건수는 요약 한 줄(`범위 밖 N건 제외`)로만 남긴다. 내용은 보여주지 않는다. *(설계자 판단: 건수는
  리뷰어가 범위를 얼마나 벗어나는지 알 수 있는 유일한 신호라 남긴다)*
- 결과적으로 모든 발견이 diff 안이므로, 원형의 `in_diff` 필드는 없어진다. LLM 이 판단하던 `in_diff` 를 계산으로 대체한다.
- 단, **인라인을 못 붙이는 경우는 여전히 있다** — 로컬과 PR head 불일치, uncommitted 변경, 422 재시도. 이때는 요약 본문만
  게시되는데, 원형 요약은 minor·nit 목록과 개별 fix 를 담지 않아 발견 상세가 PR 에서 사라진다. 그래서 인라인을 생략하거나
  실패한 경우 **본문에 `## 인라인 생략된 발견` 절을 두고 모든 발견의 4줄 코멘트를 위치와 함께** 넣는다(심각도별 `<details>`).
  *(Codex 검증 반영)*
- 리뷰어 프롬프트에도 변경 줄 범위를 알려준다(헛수고를 줄이기 위해). 강제는 필터가 한다.

### 3. 회차 기록 — 수렴 장치

리뷰할 때마다 기록을 남기고, 다음 리뷰는 그 기록을 받고 시작한다.

- 위치: `$(git rev-parse --git-common-dir)/deep-review/<브랜치>.json`. 커밋되지 않고 `.gitignore` 도
  건드리지 않으며 worktree 끼리 공유된다. 로컬 전용(혼자 쓴다).
- 브랜치 이름은 파일 이름으로 인코딩한다(`feature/x` 가 하위 디렉터리가 되지 않게). **detached HEAD**(rebase 중 등)에서는 기록을
  읽지도 쓰지도 않고 리뷰만 하며, 그 사실을 결과에 알린다 — 서로 다른 작업이 `HEAD` 한 파일에 섞이지 않게.
- 기록 JSON 이 손상돼 읽을 수 없으면 `<파일>.corrupt-<시각>` 으로 옮기고 새로 시작하며 그 사실을 알린다. 매 실행이 크래시하는
  종점을 만들지 않는다.
- 내용: 회차 번호, 각 회차의 발견(id `R<회차>-<번호>`, 차원, 심각도, 위치, 제목, tldr, fix, 현재 코드에 다시 대응시키기 위한
  그 자리의 줄 내용과 주변 문맥), 사용자가 보류한 id 와 그 보류가 굳은 시점의 코드 스냅샷, 판단 충돌에서 버린 쪽·채택한 쪽.

**판단 충돌** — 새 발견이 이전 회차 발견과 **같은 자리**를 가리키면, 그 이전 발견을 검증자에게 함께 넘긴다.
"같은 자리" = **현재 위치로 대응된 이전 발견을 포함하는 현재 diff hunk** 안에 새 발견이 있는 것. 수정은 사람이 직접 하므로
엔진은 "어느 줄이 fix 로 바뀌었는지" 알 수 없다 — hunk 단위로 정의하면 추가 스냅샷 없이 결정론적으로 판정된다.
검증자는 둘 중 하나로 판정한다:

- **새 문제** — 이전 수정이 실제로 새 버그를 만들었다. 일반 발견으로 처리한다(진짜 버그를 숨기지 않는다).
- **판단 왕복** — 새 지적이 이전 지적을 되돌리라는 것이거나, 두 지적이 동시에 만족될 수 없다.
  이 경우 "고쳐라" 로 내지 않는다. 요약의 `## 판단 충돌` 절에 *1회차 판단 / 이번 판단* 을 나란히 보여주고
  결정을 사람에게 맡긴다. **판정에 넣지 않는다.**

**충돌의 해소** — 사람은 동의하지 않는 쪽의 id 를 `--skip` 한다(별도 인수를 만들지 않는다 — 사용자 결정).
- 이전 판단이 맞다 → 이번 지적을 `--skip R2-1`.
- 이번 판단이 맞다 → 이번 지적대로 고치고 이전 지적을 `--skip R1-3`. 이후 그 자리를 이전 쪽으로 되돌리라는 지적은
  보류로 접힌다.
- 보류 규칙을 그대로 따른다 — 그 줄이 다시 바뀌면 풀린다. 이렇게 해서 같은 자리의 충돌이 회차마다 되살아나지 않는다.
- 기록에는 어느 쪽을 버렸는지(`R1-3 을 버리고 R2-1 채택`)를 남겨, 다음 회차의 `판단 충돌`·보류 표시에 그 결정을 보여준다.
- **채택된 판단을 거스르는 새 지적은 보류로 접는다.** 새 발견이 "판단 왕복" 으로 판정되고 그 상대가 채택 기록이 있는 발견이면,
  `판단 충돌` 절로 다시 올리지 않고 `[보류됨 · R1-3 기각에 따름]` 으로 접는다. 버린 쪽 발견(R1-3)이 줄 내용 변화로 현재 코드에
  대응되지 않아도, 채택된 쪽(R2-1)의 hunk 로 판정하므로 왕복이 다시 열리지 않는다.
- "그 줄이 바뀌었다" 의 기준은 **발견 시점이 아니라 보류가 굳은 시점의 코드**다(아래 보류 절). 이번 판단대로 고친 뒤
  이전 id 를 보류하면 이전 발견 시점의 코드와는 이미 다르기 때문에, 발견 시점 기준이면 보류가 즉시 풀려 왕복이 재발한다
  (Codex 검증 반영).

충돌 판정 규칙 *(설계자 판단)*:
- 충돌 판정은 "발견이 맞는가" 를 보는 **같은 검증자가 같은 호출에서** 함께 낸다(스키마에 필드 하나 추가).
  발견이 기각되면 충돌 판정은 쓰지 않는다.
- 표가 갈리면(1대1 포함) **새 문제** 쪽이다. 버그를 숨기는 것이 반복보다 나쁘다(반목표 순서).
- 검증자가 0명인 등급(빠른 모드 minor, 모든 nit)이 충돌 자리에 오면 검증 없이 `판단 충돌` 절로 보낸다.
  이 등급은 원래 판정을 바꾸지 않으므로 숨겨지는 것이 없다.

**기록의 수명** *(설계자 판단)*:
- 기록은 브랜치 단위로 이어 쓴다. 커밋 전 → push 전 → PR 사이에 끊지 않는다(그래야 수렴 장치가 시점을 넘어 작동한다).
- 이전 발견 중 **이번 대상의 범위 안에 있는 것만** 충돌 후보·보류 이월 대상이 된다. 몇 주 전 `main` 위의 무관한 리뷰는
  범위에 들지 않으므로 자연히 무시된다.
- **merge-base 변경으로 기록을 초기화하지 않는다.** 최신 기본 브랜치로 rebase·병합만 해도 merge-base 가 바뀌어,
  같은 작업을 계속하는 중에 보류·충돌 기록이 사라진다(Codex 검증 반영). 대신 기록된 각 항목을 **현재 코드에 대응**시킨다 —
  위치의 줄 내용과 주변 문맥으로 현재 파일에서 찾고, 찾지 못하거나 이번 범위 밖이면 이번 회차에서는 쓰지 않는다.
  같은 이름으로 다시 만든 브랜치의 옛 항목도 이 규칙으로 자연히 걸러진다.
- 오래 대응되지 않은 항목은 정리하지 않는다. 혼자 쓰는 규모에서 브랜치별 파일이 문제 될 만큼 커지지 않는다. *(plan-verify 렌즈 4)*

**보류** — 사람이 `--skip R1-3` 으로 고치지 않기로 한 발견:

- 다음 회차에도 다시 나오되 `[보류됨 · R1-3]` 표시를 붙이고 요약의 접힌 절로 내린다. **판정에 넣지 않는다.**
- 예외: 그 자리의 코드가 **보류가 굳은 시점**과 달라졌으면 보류를 풀고 일반 발견으로 되돌린다.
  *(설계자 판단: 코드가 바뀌면 예전 결정이 유효하다고 볼 수 없다)*
- **보류가 굳는 시점** = `--skip` 후 그 항목이 **처음으로 현재 코드에 대응된** 리뷰(대개 바로 다음 리뷰). 그 리뷰에서 그 자리의 현재 코드를 스냅샷으로 기록하고, 이후 회차는 이 스냅샷과
  비교한다. `--skip` 과 다음 리뷰 사이의 수정(충돌을 이번 판단대로 고치는 경우)은 풀림 조건이 되지 않는다 — 사람이 "고치고
  skip" 과 "skip 하고 고치기" 중 어느 순서로 해도 같게 동작한다. *(Codex 검증 반영 · 설계자 판단)*
- `--skip` 는 **기록만 고치고 끝난다.** 리뷰를 다시 돌지 않는다(보류 한 번에 5분을 붙이지 않는다). *(설계자 판단)*
- 존재하지 않거나 이미 보류된 id 면 기록을 바꾸지 않고 이번 브랜치의 유효한 id 목록을 보여준다. 성공하면 보류한 지적의 제목을
  되읊는다 — 오타로 다른 지적을 접어 버그를 숨기지 않게.
- **이유 메모**를 붙일 수 있다(`--skip R1-3 "이미 위에서 막혀 있음"`). 메모는 기록과 다음 출력의 보류 표시에 보여주기만 하고
  재검증하지 않는다. "결함이 아님" 과 "안 고침" 을 나누지 않는다(사용자 결정) — 재검증은 사람과 AI 사이에 새 왕복을 만든다.
- 보류를 되돌리는 인수는 두지 않는다. 그 자리 코드가 바뀌면 자동으로 풀리고, 실수한 경우는 기록 JSON 을 직접 고친다(README 에
  한 줄). *(plan-verify 렌즈 4)*
- 보류 항목은 리뷰어가 다시 냈는지와 상관없이 **기록에서 이월**한다. 단 이번 대상의 범위 안에 있고 보류가 굳은 시점의 스냅샷과 같을 때만.
  범위 밖이면 보여주지 않는다(범위 필터가 보류보다 먼저다). 리뷰어가 같은 자리에 같은 지적을 다시 내면 이월 항목과 합친다.
  *(설계자 판단)*

이전 발견을 현재 코드에 대응시키는 방법(줄 이동 추적, 문맥 비교 범위)은 빌더에게 맡긴다. 단, 대응과 "같은 자리" hunk 판정은
**결정론적 코드**가 하고 LLM 은 "새 문제 / 판단 왕복" 판정만 한다.

### 4. 수정 제안도 검증

검증자는 발견이 맞는지와 함께 **제안된 fix 가 새 문제를 만들지 않는지**도 본다.
fix 가 위험하다고 판정되면 발견은 남기고 fix 코드를 빼며 `→ Fix` 줄에 그 이유를 한 줄로 쓴다.
다음 회차에 뒤집힐 제안을 처음부터 줄이기 위해서다.

fix 집계와 출력 *(Codex 검증 반영 · 설계자 판단)*:
- fix 안전성은 발견을 **확인한** 검증자들만 판정한다. 그중 **한 명이라도** 위험하다고 하면 fix 코드를 뺀다 — 발견 판정보다
  보수적이다. 위험한 fix 가 다음 회차 왕복의 출발점이기 때문이다.
- 검증자가 없는 발견(빠른 모드 minor, 모든 nit, 검증 수 상한 초과, 시간 초과)의 fix 는 `→ Fix (미검증)` 으로 표시해 낸다.
  리뷰어의 fix 를 검증된 것처럼 보이게 출력하지 않는다.
- 기각된 발견의 fix 는 어디에도 출력하지 않는다.

### 5. 모드 2개와 시간 상한

| | 빠른 (커밋·push 전 기본) | 정밀 (PR 기본) |
|---|---|---|
| 시간 상한 | 5분 | 8분 |
| critical·major 검증자 | **2명** | 3명 |
| minor 검증자 | 0 (검증 생략 — 판정에 영향 없음) | 1명 |
| nit | 검증 생략 | 검증 생략 |

- 2명일 때: 둘 다 확인 → 확정 / 둘 다 반박 → 기각 / 1대1 → `unverified`(판정에 포함).
  관점은 "도달 가능성" 과 "이미 막혀 있는가" 를 하나씩 맡기고, "심각도 과장" 은 둘 다에게 준다.
  등급이 갈리면 무거운 쪽(원형 `settleSeverity` 와 같은 규칙).
- **2명이 1대1이면 시간이 남을 때만 세 번째 검증자를 넣는다**(사용자 결정). 세 번째는 같은 규칙(반박에서 시작, 내리기만)을
  따르고 "심각도 과장" 관점을 맡는다. 2대1 로 결론이 나면 그대로 확정·기각한다. 시간이 모자라면 `unverified` 로 남긴다.
  "충분히 남았다" 의 기준(검증자 1명 소요 시간)은 스파이크에서 잰다. 확정은 언제나 2명 이상의 동의다.
- 3명일 때: 원형 그대로.
- 시간 상한에 닿으면 끝나지 않은 검증의 발견을 `unverified` 로 두고 결과를 낸다. 차원 리뷰어 자체가 끝나지
  않았으면 그 차원은 실패로 드러낸다.
- **시간 초과로 생긴 `unverified` 도 판정에 넣는다**(사용자 결정). 버그를 숨기지 않는 쪽을 기본으로 두되, 5분 상한이 빠듯해
  검증 안 된 지적이 판정을 자주 흔들 수 있다는 우려가 있다(push-gate 실측 리뷰 1회 중앙값 210초). 스파이크와 `runs.tsv` 에서
  상한 도달 빈도를 보고 다시 판단한다.
- 검증 대상 발견 수에 상한을 둔다(심각도 높은 순). 상한을 넘는 발견은 `unverified`. 정확한 수는 빌더가
  실측으로 정한다 — 기준은 시간 상한 안에 들어오는 것.
- 사용자가 1명 검증은 "왜곡이 심하다" 고 했다. 어떤 모드에서도 critical·major 를 1명이 확정하게 만들지 않는다.

### 6. 차원 4개 — 범용 체크리스트

| 차원 | 본다 |
|---|---|
| correctness | 로직 오류·조건 반전·off-by-one, 런타임에 깨지는 타입 단언, null 미처리·삼키기, async(await 누락·경쟁·중복 실행), 에러 삼키기·실패가 성공으로 마감되는 경로, 경계값, 숫자·날짜 처리 |
| security | 인증·인가 우회, 소유자 확인 누락, 입력 검증·인젝션(SQL·명령·경로·프롬프트), 비밀값 노출·클라이언트로 새는 서버 키, 서명 검증·멱등성 누락, 안전하지 않은 역직렬화·리다이렉트 |
| architecture | 레이어·신뢰 경계 위반, 한 곳에 있어야 할 판단의 복제, 기존 유틸이 있는데 새로 만듦, 순수 로직에 I/O 혼입, 결합도 |
| test coverage | **이번 변경**이 만든 새 분기·경로·에러 처리에 대응하는 테스트 변경이 있는가. 저장소 전체 커버리지는 보지 않는다 |

- 모든 리뷰어는 시작 전에 대상 저장소의 `CLAUDE.md`·`AGENTS.md`(있으면 하위 디렉터리의 것까지, 변경 파일에
  적용되는 것)를 읽는다. 그 문서가 필수로 표시한 규칙(예: `CRITICAL`, `MUST`, `절대`)의 명백한 위반은 critical.
  문서가 없으면 범용 체크리스트만으로 리뷰한다.
- test coverage 는 테스트 관례를 언어별로 인정해야 한다(Java `src/main`↔`src/test` 미러, Python
  `test_x.py`·`tests/`, Node `*.test.*`·`__tests__/`). `team-tdd-kit` 의 관례 판정을 참고한다.
  사용자의 대상 저장소는 대부분 Java 다. test coverage 발견의 최고 등급은 major. *(설계자 판단: 테스트 누락
  자체가 배포 사고는 아니다)*
- 원형 주석의 차원 확장 방식(`DIMENSIONS` 배열에 추가하면 fan-out·검증·취합이 따라간다)을 유지한다.

#### 후보 차원 — 이번에는 넣지 않는다

원형 주석의 후보 목록을 범용 관점에서 정리했다. 이번 범위는 위 4개뿐이다. 후보를 넣을 때는
`DIMENSIONS` 배열에 항목을 하나 추가하면 되지만, 차원 하나가 리뷰어 1명과 그 발견의 검증자(빠른 2명·정밀 3명)를
늘리므로 **빠른 모드 5분 상한 안에 드는지 실측한 뒤** 넣는다.

| 후보 | 본다 | 지금 넣지 않는 이유 |
|---|---|---|
| performance | 루프 안의 I/O·N+1 쿼리, 불필요한 전체 로드, 핫패스의 동기 블로킹, 알고리즘 복잡도. 원형 후보의 "CPU/perf patterns" 를 여기에 합친다 | 실제 영향은 데이터 크기와 호출 빈도에 달려 있어 diff 만 보고는 추측이 되기 쉽다 — 틀린 리뷰가 가장 큰 불만이었다 |
| conventions | 그 저장소의 명명·구조·관용구에서 벗어남 | 대부분 nit 이라 판정을 바꾸지 않는다. 린터가 결정론적으로 더 잘 잡는다 |
| cross-file consistency | 바꾼 시그니처·계약을 쓰는 다른 파일이 따라 바뀌었는가, 짝을 이루는 파일(스키마↔타입, 설정↔코드)이 어긋났는가 | 결함이 대개 diff **밖** 파일에 있다. 범위 필터와 정면으로 부딪혀 "diff 줄에 무엇으로 앵커할지" 설계가 따로 필요하다 |
| privacy | 개인정보의 로그 출력·외부 전송·과다 수집, 보존 기간 | 상당 부분이 security 와 겹친다. 겹치지 않는 부분만 따로 떼어낼 기준이 아직 없다 |
| behavioral correctness | 변경이 기존 사용자 관점 동작(API 응답 형태·기본값·에러 메시지)을 의도치 않게 바꾸는가 | correctness 와 경계가 흐리다. 의도를 알려면 PR 설명·이슈가 필요하다 |

### 7. 출력·판정·실행 기록 보강

*(plan-verify 검증 반영)*

- **발견 ID 를 출력한다.** 층 1 코멘트의 첫 줄(`[major] R2-1 제목`), 요약의 critical/major 목록, `판단 충돌` 절, 보류 절 모두에
  id 를 붙인다. id 가 보이지 않으면 `--skip` 과 충돌 해소를 쓸 수 없다.
- **수렴을 보여준다.** 2회차부터 요약 판정 줄 아래에 `이전 회차 대비: 해결 N · 새 문제 M · 충돌 K · 보류 J · 미확인 U` 한 줄을 둔다(미확인 0 이면 생략).
  "해결" = 이전 회차의 발견 중 이번 범위 안에서 다시 나오지 않은 것. 기록만으로 계산한다.
  단 **이번 회차에 그 발견의 차원이 실패했으면 해결로 세지 않는다**(다시 안 나온 이유가 해결이 아니라 리뷰 실패다). 그런 항목은
  `미확인 N` 으로 따로 센다. *(Codex 2차 검증 반영)*
- **실패한 차원이 있으면 Approve 를 내지 않는다.** 판정 표는 발견만 보므로, 차원이 전부 시간 초과로 실패하면 발견 0건으로
  Approve 가 나온다(조용한 성공). 실패 차원이 하나라도 있고 판정이 Approve 였다면 **`Incomplete`** 로 낸다.
  Blocked·Changes Requested 는 그대로 둔다(이미 결함이 있다는 정보는 유효하다).
- **읽기 전용을 계산으로 확인한다.** 워크플로 전후로 `git status --porcelain` 과 대상 diff 의 해시를 비교한다. 다르면 결과 맨 위에
  `⚠ 리뷰 중 작업 트리가 바뀌었다` 를 띄우고 **그 회차는 기록하지 않는다**(기록의 스냅샷과 코드가 어긋나므로). 에이전트가 고친
  경우와 사용자가 리뷰 중에 편집한 경우를 같은 검사로 잡는다. 리뷰어·검증자 프롬프트에 "빌드·테스트를 실행하지 마라" 를 넣는다
  (Gradle 등이 파일을 만들고 시간 상한을 잡아먹는다).
- **실행 기록 `runs.tsv`**(사용자 결정) — `$(git rev-parse --git-common-dir)/deep-review/runs.tsv` 에 실행마다 한 줄:
  시각, 브랜치, 모드, 변경 파일 수, 변경 줄 수, 걸린 시간, 상한 도달 여부, 미검증 건수, 세 번째 검증자 투입 수, 판정.
  저장소 단위 한 파일이라 추이를 한눈에 본다(perf-loop `results.tsv` 와 같은 방식). 큰 diff 기준·시간 상한·미검증 판정 규칙을
  사람이 이 숫자로 조정한다. 자동으로 기준을 바꾸지 않는다. 재사용(지난 결과 다시 보기)·`--skip` 실행은 적지 않는다.

## 구조

perf-loop 와 같은 갈래로 나눈다 — **판단은 LLM, 계산은 엔진.**

```
plugins/team-code-review/
  .claude-plugin/plugin.json
  README.md
  skills/deep-review/SKILL.md     # 정찰 → 엔진 → 워크플로 → 엔진 → 출력·게시. 판단을 하지 않는다
  workflows/deep-review.js        # 차원 리뷰 + 검증 (원형 review-code.js 의 범용판)
  engine/*.mjs                    # 결정론: 대상 선정·diff 줄 집합·범위 필터·회차 기록·충돌 후보·판정 집계
  test/*.test.mjs                 # node --test. 의존성 없음(Node 내장만)
```

흐름:
1. 스킬이 엔진을 불러 대상·변경 줄 집합·이전 회차 기록을 얻는다. 재사용 키가 마지막 회차와 같으면 2~3 을 건너뛰고 지난 결과로
   4 로 간다(게시 포함). index 에만 있는 변경이 있으면 경고, 큰 diff 면 경고, 작업 트리 해시를 잡아 둔다
2. `Workflow({ scriptPath: '<ROOT>/workflows/deep-review.js', args })` — 플러그인 루트 찾기는
   perf-loop `SKILL.md` §0 의 방식을 따른다. 충돌 후보(이전 발견)는 args 로 넘긴다
3. 작업 트리 해시를 다시 보고, 반환을 엔진에 넣어 범위 필터·보류·충돌 처리·판정을 계산하고 회차 기록(바뀌었으면 생략)과
   `runs.tsv` 를 쓴다
4. 스킬이 출력(2층)하고, `--comment` 면 게시한다

- 워크플로 스크립트는 파일시스템에 접근할 수 없다(원형 주석). 그래서 diff 파싱·기록은 엔진이, 워크플로 밖에서 한다.
- Workflow 도구가 없는 환경이면 그 사실을 알리고 멈춘다. *(설계자 판단: perf-loop 도 같은 전제다. Agent 도구
  대체 경로는 만들지 않는다)*
- 마켓플레이스 `.claude-plugin/marketplace.json` 에 등록한다.

## 테스트 (TDD)

엔진은 전부 테스트를 먼저 쓴다. 최소 다음을 고정한다:
- diff 파싱: 추가·수정·삭제·이름 변경·바이너리·새 파일·**파일 전체 삭제**·hunk 여러 개, untracked 파일
- 좌표계: **커밋에서 바꾼 줄 앞에 미커밋으로 줄을 넣은 경우** 범위가 최종 작업 트리 좌표로 잡히는가 (Codex 재현 사례)
- 범위 필터: 경계 줄, diff 에 없는 파일, `side: 'old'` 삭제 줄, 파일 전체 삭제
- 판정: 원형 표 + 보류·충돌 제외 + unverified 포함 + 실패 차원
- 검증 집계: 2명(2-0·0-2·1-1·한 명 사망)·3명 경우, 등급 하향·상한 자르기, fix 안전성(한 명이라도 위험 → 제거)
- 회차 기록: 보류 유지, 보류가 굳은 뒤 코드가 바뀌면 해제, **이번 판단대로 고친 뒤 이전 id 를 skip 해도 보류가 유지**,
  rebase 로 merge-base 가 바뀌어도 기록 유지, 충돌 후보 선정
- PR 게시 payload: 인라인 생략·422 재시도 시 모든 발견 상세가 본문에 남는가
- 판단 충돌: "같은 자리" hunk 판정, **채택된 판단을 거스르는 새 지적이 보류로 접히는가**(버린 쪽이 대응되지 않을 때 포함)
- 보류: 잘못된 id 는 기록 불변, 이유 메모 표시, 보류가 처음 대응된 리뷰에서 굳는가
- 판정: 실패 차원 + 발견 0건 → `Incomplete`
- 기록: 브랜치 이름 인코딩(`feature/x`), detached HEAD 에서 기록 안 함, 손상 JSON 복구
- 재사용: 키가 전부 같으면 지난 결과, 한 글자 변경·모드 변경·`--fresh` → 새로, **diff 는 같고 HEAD·기준 커밋·규칙 문서만 바뀜 → 새로**,
  재사용 + `--comment` → 게시까지 진행
- index 에만 있는 변경: stage 한 삭제를 작업 트리에서 되살린 경우 → 경고 + `Incomplete`, `git add -p` 후 추가 편집 → 경고 없음
- PR base: `baseRefOid` 로 고정, 객체가 없으면 멈춤
- 수렴 요약: 차원이 실패한 이전 발견은 해결이 아니라 `미확인`
- 세 번째 검증자: 1대1 + 시간 충분 → 투입, 시간 부족 → `unverified`
- `runs.tsv` 한 줄 형식, 재사용·skip 은 기록 안 함
- 대상 선정: 표의 각 행, upstream 없음, 기본 브랜치 감지 실패

워크플로·스킬은 FinSight 저장소에서 원형과 나란히 돌려 회귀를 본다:
같은 변경에 대해 원형이 낸 범위 안 발견을 새 스킬도 내는가, 범위 밖 발견이 0건인가,
**지적을 고친 뒤 재실행했을 때 같은 자리를 되돌리라는 지적이 "판단 충돌" 로 가는가**,
빠른 모드가 5분 안인가.

## 먼저 실증할 것

- **시간 상한의 강제와 부분 결과 반환.** 5분·8분 상한은 Workflow 안에서 진행 중인 에이전트를 끊고 끝난 결과만으로 반환할 수
  있어야 성립한다. 이것이 되는지 구현 첫 단계에서 버리는 스파이크로 확인한다. 안 되면 상한을 지키는 다른 방법(검증 수 상한을
  더 낮추기 등)을 정하고 이 문서를 고친 뒤 진행한다. *(Codex 검증에서 미실증으로 지적)*
- **상한 도달 빈도와 기준값.** 같은 스파이크로 FinSight 최근 커밋 10개 정도를 빠른 모드로 돌려 커밋마다 걸린 시간, 상한 도달 여부,
  미검증 건수, 변경 줄 수, 검증자 1명 소요 시간을 잰다. 여기서 세 가지를 정한다:
  (1) 시간 초과 `unverified` 를 판정에 넣는 규칙을 유지할지(자주 닿으면 다시 논의),
  (2) 큰 diff 경고 기준 줄 수(몇 줄부터 5분을 넘기 시작하는가),
  (3) 세 번째 검증자를 넣을 만큼 "시간이 남았다" 의 기준.

## 빌더에게 맡기는 것

- 엔진 파일 분할과 이름, 회차 기록 JSON 의 정확한 스키마
- 줄 이동 추적 방법(이전 회차 위치 → 현재 위치 대응)
- 검증 대상 발견 수 상한값, 시간 상한을 워크플로에서 강제하는 방법
- 범용 체크리스트 문구 다듬기, 검증 관점 문구의 범용화(원형 2번 관점의 "RLS, 마이그레이션" 같은 FinSight 어휘 제거)
- 중복 병합 규칙(원형은 `file:line` 만으로 병합해 같은 줄의 다른 결함을 잃는다 — 고쳐도 된다)

## 감수한 트레이드오프

| 선택 | 감수하는 것 |
|---|---|
| push 전 범위 강제 인수 없음 | uncommitted 가 있으면 push 안 한 커밋은 리뷰되지 않는다. 전체를 보려면 먼저 커밋한다 |
| 시간 초과 `unverified` 도 판정에 포함 | 5분이 빠듯하면 검증 안 된 지적이 Changes Requested 를 낼 수 있다 — 실측 후 재논의 |
| `--skip` 하나로 "결함 아님" 과 "안 고침" 을 함께 처리 | 리뷰가 틀린 경우가 기록에서 따로 구분되지 않는다(메모로만 남는다) |
| 보류 되돌리는 인수 없음 | 실수로 보류한 것은 기록 JSON 을 직접 고쳐야 한다 |
| 큰 diff 는 경고만 | 사용자가 무시하고 진행하면 불완전한 결과(`Incomplete`·미검증)를 받는다 |
| 리뷰 중 작업 트리가 바뀌면 그 회차를 기록하지 않음 | 리뷰 중에 편집하면 그 회차의 수렴 기록이 남지 않는다 |
| 범위 밖 비율 경고·결과 원본 저장 없음 | 건수 줄 하나로만 이상을 알아챈다, 엔진이 실패하면 다시 돌려야 한다 *(렌즈 4 철회)* |
