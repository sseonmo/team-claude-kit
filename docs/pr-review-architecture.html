PR 자동 리뷰 — 구조와 이식 가이드

파일 8개와 job 2개가 PR 하나를 채점해 risk:* 라벨을 붙이고, 조건이 맞으면 사람 없이 머지한다. 이 문서는 그 구조를 설명하고, 같은 것을 다른 저장소에 옮길 때 무엇을 그대로 쓰고 무엇을 새로 써야 하는지까지 다룬다.

01 · 먼저 알아야 할 말 다섯 개

이 문서와 코드 주석에 반복해서 나오는 말들이다. 여기서 뜻을 고정하고 시작한다.

루브릭
채점 기준 체계 전체. 어떤 축을 볼지, 축마다 몇 점인지, 총점이 어느 구간이면 어떤 등급인지. 이 저장소에서는 rubric.mjs 와 prompt.mjs 두 파일에 나뉘어 있다.
앵커
루브릭 안에서 "몇 점을 언제 주는가"를 구체적 사례로 못 박은 항목. 닻(anchor)처럼 척도를 고정시켜 점수가 호출마다 흔들리지 않게 한다. "보안 위험 0~30점"만 주면 매번 다른 답이 나오지만, "클라이언트에서 API 키 접근 = 30점"은 판정할 수 있다.
점수
위험도다. 높을수록 나쁘다. 품질 점수가 아니라서 100점이 최고가 아니라 최악이다. 실질적 의미는 하나 — 사람 손을 타느냐 마느냐. 15점 이하만 무인 통과한다.
배선
판정을 하지 않고, 판정하는 함수들을 올바른 순서·올바른 인자로 불러주는 코드. review.mjs 가 그것이다. 계산기가 정확해도 잘못된 값을 넣으면 방어가 죽는다. 이 저장소의 사고 3건이 전부 여기서 났다.
fail-open
fail-closed
판정할 수 없을 때 통과시키느냐(open) 막느냐(closed). 이 시스템은 둘을 섞어 쓴다 — job 은 fail-open, 자동 머지는 fail-closed. 막히는 비용은 사람이 한 번 보는 것이고, 잘못 머지되는 비용은 되돌릴 수 없다.

02 · 무엇이 무엇을 부르는가

실행 주체는 워크플로 하나뿐이고, 나머지는 전부 review.mjs 가 엮는다. 눈여겨볼 것은 모든 모듈이 rubric.mjs 로 수렴한다는 점이다. 점수 구간도, 심각도 목록도, 라벨 이름도 거기 한 벌만 있다.

어느 저장소에서나 같은 코드 저장소가 정하는 정책 값이 들어 있음

파일별 책임

파일줄하는 일테스트
review.mjs149 배선 — git 실행, 호출 순서, 분기, 종료코드review.test.mjs (103줄)
rubric.mjs115 배점·등급 구간·심각도 집계·자동 머지 판정rubric.test.mjs (165줄)
prompt.mjs213 앵커표·프로젝트 규칙·응답 스키마·OpenAI 호출없음
render.mjs76 코멘트 마크다운 생성render.test.mjs (116줄)
github.mjs66 코멘트 upsert · risk:* 라벨 교체없음

prompt.mjs 에 테스트가 없는 것은 내용이 대부분 프롬프트 문자열이기 때문이다. 다만 스키마와 callOpenAI 는 코드라서, 옮길 때는 이 둘을 앵커 문자열과 분리해서 봐야 한다.

03 · PR 이 열리면 벌어지는 일

트리거는 opened · synchronize · reopened 셋이다. 즉 PR 을 열 때뿐 아니라 커밋을 밀 때마다 매번 다시 돈다. job 은 둘로 나뉘고, 그 경계에서 오가는 것은 값 세 개뿐이다.

04 · PR 이 오가는 상태

점수는 네 구간으로 갈리고, 그 위에 지적 심각도가 한 겹 더 얹힌다. 총점이 아무리 낮아도 medium 이상 지적이 하나 있으면 자동 머지는 닫힌다. 판정 불능(unknown)도 같은 취급이다.

총점등급지적이 없거나 lowmedium 이상 · unknown
0–15risk:low 자동 머지사람 승인 대기
16–35risk:medium 사람 승인 대기사람 승인 대기
36–60risk:high 대기 + 2차 딥리뷰대기 + 2차 딥리뷰
61–100risk:critical job 실패job 실패

05 · 채점 기준 전문

루브릭은 두 곳에 나뉘어 있다. 숫자 뼈대는 rubric.mjs 에, 사례(앵커)는 prompt.mjs 의 문자열에 있다. 옮길 때 둘을 따로 봐야 하는 이유다.

축과 배점 — rubric.mjs:4

축만점누가 매기는가
보안30gpt-5
스코프20코드 — files×0.4 + lines/200, 상한 20
Breaking change20gpt-5
테스트 커버리지15gpt-5
되돌리기 비용15gpt-5

스코프만 코드가 계산한다. 셀 수 있는 값이라 LLM 에 맡기지 않는다 — 호출마다 점수가 흔들리는 것을 막는다.

앵커표 전문 — prompt.mjs:59

아래 표는 프롬프트에 그대로 들어간다. 함께 붙는 지시는 "이 표의 상황에 정확히 해당할 때만 그 점수를 준다. 애매하면 낮은 쪽을 택한다" 이다. 오른쪽 꼬리표는 다른 저장소로 옮길 때의 성격이다.

17행 중 9행이 전용이다. 그리고 전용 9행은 다시 두 부류로 갈린다 — 경로만 갈아 끼우면 되는 것 6개(src/lib, src/types, src/app/api, src/services)와 그 저장소가 무엇을 지키기로 했는지 알아야 나오는 것 3개 (LAYOUT_MISMATCH, 프롬프트 계약, 출력 규격).

표에 붙어 있는 단서

가드레일 자체를 바꾸는 변경은 src/ 밖에 있어도 보안 축으로 채점한다. 완화든 강화든 마찬가지다 — 게이트를 조이는 변경도 잘못 조이면 그 자체가 사고이고, 그걸 판단하는 건 그 게이트가 아니라 사람이어야 한다.

이 두 줄이 없던 동안, 저장소의 유일한 위험 명령 차단 훅을 삭제한 PR 이 보안 0/30 · 총점 6점(risk:low)으로 자동 머지됐다. 리뷰어는 그 PR 에 medium 지적을 적어두고도 점수는 0 을 줬다 — 앵커에 없는 상황은 채점되지 않기 때문이다.

지적 심각도 — prompt.mjs:145

점수와 별개로 리뷰어는 findings 에 지적을 적고 각각 심각도를 매긴다. 이게 자동 머지의 두 번째 관문이다.

심각도기준자동 머지
high 되돌리기 어렵거나 사고가 이미 나 있는 것 — 키 유출, 데이터 손실, 아키텍처 규칙 위반, 검증 장치(훅·CI 게이트·머지 조건) 약화차단
medium 지금은 안 터지지만 조건이 갖춰지면 터지는 것 — 경계·예외 처리 누락, 새 코드에 테스트 없음, 다음 편집이 자연스럽게 깨뜨릴 암묵적 전제차단
low 고치면 좋지만 방치해도 동작에 영향이 없는 것 — 문서·주석·네이밍 정합성 통과
unknown 스키마에 없는 값이 왔거나 응답이 깨진 경우차단 (fail-closed)

06 · 점수를 직접 매겨보기

같은 변경이라도 테스트 하나로 결과가 갈린다. 실제 계산을 두 번 따라가 본다.

사례 A — 함수 시그니처를 바꾸고 테스트를 안 붙였다

파일 10개 · 400줄 변경 · src/lib/layout.ts 공개 함수 인자 추가

스코프10×0.4 + 400/2006
Breakingsrc/lib/* 시그니처 변경8
테스트대응 .test.ts 변경 없음15
보안 · 되돌리기해당 없음0
총점29

→ risk:medium · 자동 머지 안 됨. 리뷰어는 아마 [test/medium] 지적도 함께 남긴다.

사례 B — 같은 변경인데 테스트를 붙였다

스코프파일 11개 · 460줄6
Breakingsrc/lib/* 시그니처 변경8
테스트테스트 같이 수정됨0
총점14

→ risk:low · 지적이 없거나 low 뿐이면 사람 승인 없이 squash 머지되고 브랜치까지 삭제된다.

여기서 자주 헷갈리는 것

한 축에서 여러 앵커에 해당해도 점수는 더해지지 않는다. 응답 스키마가 축당 score 하나만 받기 때문에, 리뷰어가 가장 맞는 앵커 하나를 골라 그 값을 낸다. 앵커표는 그 값을 고를 때 보는 참조표지 체크리스트가 아니다.

근거가 없으면 0점이다. 리뷰어가 점수를 줘도 evidence(diff 인용)가 비어 있으면 normalizeAxes 가 그 축을 0 으로 강등한다(rubric.mjs:38). 지어낸 점수를 막는 장치다.

07 · 다른 저장소로 옮기기

절차

  1. 01
    파일을 복사한다 
    scripts/pr-review/*.mjs   → 그대로
.github/workflows/pr-review.yml → 그대로

    테스트를 돌릴 러너가 없으면 *.test.mjs 는 일단 두고 러너를 나중에 붙인다.

  2. 02
    저장소 설정 두 가지를 만든다
    • OPENAI_API_KEY 를 저장소 secret 에 등록 (Settings → Secrets → Actions)
    • risk:* 라벨은 만들 필요 없다 — 없으면 GitHub 이 자동 생성한다(github.mjs:50)
  3. 03
    경로 6행을 새 경로로 치환한다

    그 저장소에서 API 경계 · 공개 타입 · 핵심 로직 · 테스트 대상이 어디인지 찾아 src/app/api, src/types, src/lib, src/services 자리에 넣는다. Python 이면 api/·models/·core/ 같은 것이 대응된다.

  4. 04
    도메인 3행을 새로 쓴다

    "이 저장소에서 없애면 안 되는 검증은 무엇인가", "바꾸면 되돌리기 힘든 계약은 무엇인가" 두 질문의 답이 그 자리에 들어간다. 답이 없으면 그 행은 빼는 것이 낫다 — 맞지 않는 앵커는 오채점을 만든다.

  5. 05
    PROJECT_CONTEXT 를 새로 쓴다

    prompt.mjs:108. 지금 것은 CLAUDE.md 의 아키텍처 규칙을 옮겨 적은 것이다. 같은 방식으로 그 저장소의 CLAUDE.md 에서 가져오면 된다 — 단, 아래 경고를 먼저 볼 것.

  6. 06
    등급 구간과 자동 머지 상한을 검토한다

    rubric.mjs:63 의 15/35/60 과 rubric.mjs:85 의 AUTO_MERGE_MAX_SEVERITY = 'low'. 혼자 쓰는 저장소가 아니거나 되돌리기 비용이 크면 자동 머지를 아예 끄는 편이 낫다 — automerge job 을 지우면 된다.

  7. 07
    드라이런으로 확인한다 
    DRY_RUN=1 BASE_REF=main OPENAI_API_KEY=… node scripts/pr-review/review.mjs

    git fetch 와 GitHub API 를 건너뛰고 코멘트를 stdout 으로만 낸다. 점수가 전부 0 으로 나오면 앵커가 그 저장소에 맞지 않는다는 신호다.

CLAUDE.md 를 믿기 전에 — 2026-08-09 실측

PROJECT_CONTEXT 를 CLAUDE.md 에서 가져오는 방식은 그 파일이 사실을 적고 있을 때만 성립한다. 실제 저장소 6곳을 확인한 결과는 이렇다.

저장소CLAUDE.md쓸 수 있는가
stock_manager12.4 KB충실
sogongdam5.1 KB보통
harness_framework0.9 KB템플릿 그대로
chat · team-claude-kit · kimdev-folio없음불가

harness_framework 것은 {절대 지켜야 할 규칙 1} 같은 플레이스홀더가 채워지지 않은 채고, Python 저장소인데 내용은 Next.js·npm 기준이다. 그대로 프롬프트에 넣으면 존재하지도 않는 app/api 를 기준으로 채점하게 된다.

CLAUDE.md 는 "지키기로 한 것"의 선언이지 사실의 보증이 아니다. 옮기기 전에 그 파일이 실제 구조와 맞는지 눈으로 확인하고, 맞지 않으면 PROJECT_CONTEXT 는 손으로 쓰는 편이 낫다.

08 · 알려진 함정

배선은 테스트되지 않는다

rubric.mjs 의 함수들은 테스트 165줄이 지키지만, 그것들을 잇는 코드가 틀리면 함수가 정확해도 방어가 죽는다. 실제로 이 저장소의 사고 3건이 전부 배선에서 났고, 그 흔적이 review.mjs:81 주석에 남아 있다. 

// 판정에는 **원본**을 넘긴다. 여기서 먼저 [] 로 눌러버리면 maxSeverity 가 보는 것은
// 언제나 정상 배열이라 'unknown'(판정 불능 → 머지 차단) 경로가 도달할 수 없게 된다.
const severity = maxSeverity(first.findings)                        // ← 원본
const findings = Array.isArray(first.findings) ? first.findings : [] // ← 렌더링용

두 줄의 순서를 바꾸면 unknown 분기가 도달 불가능해지는데, 테스트는 전부 통과한다. 함수 자체는 멀쩡하기 때문이다.

DRY_RUN 이 가리는 구간

review.test.mjs 는 DRY_RUN=1 로 배선을 실제 실행해 검증한다. 그런데 DRY_RUN 은 코멘트를 찍고 review.mjs:103 에서 바로 반환하므로, 그 아래의 canAutoMerge 호출(116행)과 job output 기록(129행)은 테스트가 지나지 않는다. 자동 머지 판정 배선만 무커버리지로 남아 있다.

fail-open 과 fail-closed 가 섞여 있다

상황job자동 머지
OpenAI 호출 실패 · 응답 깨짐통과 (fail-open) 차단 — output 을 못 씀

총점 61 이상 (critical)실패 job 자체가 안 뜸

의도된 설계다 — 훅의 fail-open 은 "판정 못 하면 사용자 작업을 막지 않는다"이고, 여기서 통과는 사람 승인 없는 머지다. 막히는 비용은 사람이 한 번 보는 것이고, 잘못 머지되는 비용은 되돌릴 수 없다(rubric.mjs:90 주석).

이 저장소가 감수하기로 한 것

  • 테스트 통과 여부를 확인하지 않는다. 머지되면 곤란한 PR 은 draft 로 연다.
  • 게이트 자신의 코드를 바꾸는 PR 도 같은 경로로 통과한다. 경로 기반 예외를 넣자는 제안은 세 번 기각됐다.
  • diff 에 없는 것은 리뷰에 없다. 빠진 방어를 추가하지 않은 PR 은 지적되지 않는다.

Free 플랜 private 저장소라 branch protection 을 쓸 수 없고(API 403), 워크플로가 유일한 수단이라 그 안에서 속도를 택한 결과다. 다른 저장소에 옮길 때 같은 전제가 성립하는지 먼저 확인할 것. 여러 사람이 쓰는 저장소라면 automerge job 을 지우고 라벨과 코멘트만 쓰는 편이 낫다.
